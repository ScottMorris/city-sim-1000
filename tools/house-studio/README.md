# House Studio — 3D-to-pixel-art building generator

A reusable pipeline for generating game-ready building sprites: model a house procedurally in Blender (headless, via Docker — no local Blender install needed), render it from a fixed dimetric angle, then pixelate and composite the render into the tile-art style the rest of `app/public/assets/tiles/buildings/` already uses.

This exists because the game's existing `res-house-*.png` sprites are AI-image-gen output with no reproducible source. This pipeline is the reproducible alternative: a parametric 3D model with named, tunable proportions, so new building variants can be generated by adjusting numbers rather than re-prompting an image model.

## Requirements

- Docker (for headless Blender — no local Blender install needed)
- Python 3 with Pillow (`pip install pillow`) for the pixelation/compositing step

## Usage

1. Render the 3D model:

   ```bash
   docker run --rm \
     -v "$(pwd)/tools/house-studio:/scripts" \
     -v "$(pwd)/tools/house-studio/out:/out" \
     nytimes/blender:3.3.1-cpu-ubuntu18.04 \
     blender --background --python /scripts/build_house.py
   ```

   Produces `tools/house-studio/out/house.png` — a 640×640 transparent-background render.

2. Pixelate and composite it into a game sprite:

   ```bash
   python3 tools/house-studio/pixelate_and_composite.py \
     tools/house-studio/out/house.png \
     tools/house-studio/out/house_pixelated.png \
     [pixel_grid]
   ```

   `pixel_grid` is optional (defaults to 60 — see "Why 60?" below).

## How it works

### The 3D model (`build_house.py`)

A single-storey gable-roofed house, built as plain `bpy`/`bmesh` calls (no external assets):

- **Wall box + gable caps**, joined and welded (`bmesh`/`remove_doubles`) into one seamless mesh. Keeping the wall, the gable-end triangular caps, and the roof as a single mesh — rather than separate objects that merely touch — matters: Blender's Freestyle line renderer outlines every open mesh boundary, so any two pieces that are only *positioned* against each other (not actually welded) show up as a stray black seam line, even when they're perfectly coplanar.
- **Roof overhangs preserve the pitch.** The eave overhang extends the rafter line along its existing slope (dropping in Z as it extends in Y), not sideways at a constant height — the latter silently flattens the pitch. The rake overhang (past the gable ends) is a pure X-extension, which doesn't touch the pitch at all since the slope is only a function of Y.
- **Gable ends are flush** (no overhang) so the wall reads as continuing flat to the ridge, matching the reference sprite's look — this was reverse-engineered from the reference via a manual pixel-classification sweep (sampling a grid of the reference image and classifying each cell by colour) rather than guessed from eyeballing it.
- **Toon/cel shading**, not Principled BSDF. This is the single biggest lever for reading as *hand-drawn* rather than *a 3D render that got posterized*: a surface's lighting term is computed as `Normal · light-direction` (plain vector math against a fixed light-direction constant, matching the key sun), then immediately quantized through a hard 2-band `ColorRamp` (`CONSTANT` interpolation) into a flat light/shadow multiplier, then multiplied onto the surface's own flat/patterned colour and output via Emission — so nothing downstream can soften it back into a gradient. Fill light and world ambient are kept low; enough directional contrast has to survive for the light/shadow split to mean anything. (An earlier version used `ShaderNodeShaderToRGB` for the lighting term instead — don't reintroduce it. Sampling its raw output directly showed an exact constant value on every surface in the scene regardless of orientation, a known Cycles reliability gap, not a real per-pixel lighting evaluation. It happened to go unnoticed on flat faces because the visible "shading contrast" there was actually just each face's own siding/shingle band colour, but it left curved geometry — the bush — completely flat. The N·L approach is deterministic and doesn't depend on that node at all.)
- **Siding and shingle textures are low-frequency wave patterns**, not fine repeating checkers/bricks. A high-frequency procedural texture (the first attempt used `ShaderNodeTexBrick` for shingles) aliases into pure static once point-sampled down to sprite resolution — texture frequency has to be chosen relative to the *target* pixel grid, not the render resolution.

### Pixelation (`pixelate_and_composite.py`)

- Crops tight to the render's alpha bounding box, then **point-samples (`NEAREST`)** down to the target grid — not box-averaging. Box-filtering blends the black outline into its neighbours proportionally, which reads as a washed-out grey line rather than the solid black of hand-drawn pixel art. `NEAREST` keeps outline pixels solid black; the tradeoff is texture noise if the grid is too fine relative to the render's own detail frequency.
- **Why 60?** Compared 40/60/80 directly: 40 is coarse enough that `NEAREST` sampling starts dropping thin lines (gaps in the outline), 80 resolves so much of the render's own micro-detail that it reads as noisy rather than deliberate, 60 is the sweet spot — solid unbroken linework without the higher grid's noise.
- Binary alpha threshold at the silhouette (no antialiased edge fade) + a light posterize on RGB, so gradients read as a few deliberate flat tones rather than a smooth ramp.

## Tuning

All the geometry/material knobs are named constants near the top of `build_house.py` (`WALL_W`/`WALL_D`/`WALL_H`, `ROOF_H`, `ROOF_OVERHANG_EAVE`/`_RAKE`, `WIN_W`/`WIN_H`, `BUILDING_ROTATION_DEG`, etc.) — adjust and re-render rather than hand-editing geometry. `BUILDING_ROTATION_DEG` rotates the whole model around Z; since the camera sits at a fixed 45° azimuth (the classic dimetric angle), only offsets that keep it away from exact 45°-multiples-off-the-current-angle give a proper two-face corner view — an offset of exactly 45° from a good angle points a flat face straight at the camera instead.

## Known limitations / next steps

- No grass/ground-plane compositing yet — output is the house alone on a transparent canvas. (In progress — see the branch this landed on.)
- Only one gable end has window/door detail, so `BUILDING_ROTATION_DEG` values that face the *other* gable toward the camera show a blank wall.
- Single house variant only; no recipe/variant system yet (contrast with `app/scripts/build-park-assets.mjs`, which composites pre-drawn SVG art rather than generating geometry).
